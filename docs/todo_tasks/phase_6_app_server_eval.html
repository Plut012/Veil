Date: 2026-05-24  |  Status: COMPLETE  |  Phase dependencies: Phase 1 (Crypto), Phase 2 (Identity), Phase 3 (Envelope), Phase 4 (Bridge), Phase 5 (Pairing)

Component Purpose

The app server is the orchestrator. It connects every backend module — crypto, identity, bridge, envelope, pairing — and exposes them to the frontend via a WebSocket API. It also serves the built Svelte frontend as static files.

Two parts make up this phase: config (TOML loading/saving for persistent settings) and server (FastAPI + WebSocket routing + lifecycle management). The server is the only module that knows about all other modules. Everything else is decoupled.

WebSocket Message Protocol

Client  →  Server:
  { type: "send_message",    contact_id: str, text: str }
  { type: "list_contacts" }
  { type: "initiate_pairing" }
  { type: "complete_pairing", qr_data: str }
  { type: "update_envelope",  template: str }
  { type: "set_theme",        theme_id: str }

Server  →  Client:
  { type: "connected",        status: "ok" }
  { type: "contacts",         contacts: [...] }
  { type: "message",          contact_id, text, direction: "in"|"out" }
  { type: "pairing_qr",       qr_image: "<base64 PNG>" }
  { type: "pairing_complete", contact: { contact_id, display_name, telegram_channel_id } }
  { type: "error",            message: str }

Message Flow Diagrams

Outgoing

Frontend → WebSocket { type: "send_message", contact_id, text }
  → VeilApp.send_message()
    → encrypt(text, contact.key)              # XChaCha20-Poly1305
    → base64url_encode(sealed)
    → wrap(ciphertext_b64, envelope_template) # user's envelope style
    → bridge.send(channel_id, envelope)       # dumb pipe to Telegram
    → _broadcast { type: "message", direction: "out" }

Incoming

Telegram API → bridge callback(channel_id, message_text)
  → VeilApp._handle_incoming()
    → if pending pairing: try parse_handshake_message()
        → complete_pairing_as_initiator()
        → _broadcast { type: "pairing_complete" }
    → get_contact_by_channel(channel_id)
    → unwrap(message_text, [contact.envelope_template])
    → base64url_decode → decrypt(sealed, contact.key)
    → _broadcast { type: "message", direction: "in" }

Implementation Notes

  • Config uses tomli / tomli_w directly: Both were already declared in pyproject.toml. tomli reads binary, tomli_w writes binary — both use "rb" / "wb" file modes as required by the respective libraries.
  • VeilApp._broadcast cleans up dead clients: Any WebSocket that raises during send_text is collected in a disconnected set and removed from _ws_clients after the iteration. This avoids mutating the set during iteration and accumulation of stale connections.
  • Frontend static files are optional: create_app() only mounts the frontend/dist directory if it exists. The server starts cleanly without a built frontend, which is important during backend-only development.
  • Lifespan manages bridge lifecycle: FastAPI's asynccontextmanager lifespan ensures veil.start() runs before accepting requests and veil.stop() runs on shutdown — even if an exception occurs. This guarantees the Telethon client is always disconnected cleanly.
  • Initial state on WebSocket connect: On each new connection, the server immediately sends a connected message followed by a contacts list. This lets the frontend render the contact list without waiting for an explicit request.
  • Pending pairing is checked first: _handle_incoming checks for a pending pairing handshake before any contact lookup. This is intentional — a handshake arrives in a new channel before the contact exists in the store.
