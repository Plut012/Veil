Date: 2026-05-24  |  Status: COMPLETE  |  Phase dependencies: Phase 1 (Crypto Engine), Phase 2 (Identity Store)

Component Purpose

The Telegram bridge connects Veil to Telegram using the Telethon user client. It authenticates as the user's Telegram account, sends encrypted envelopes to dedicated channels, receives messages from those channels, and creates new channels during the pairing ceremony.

The bridge is a dumb pipe. It never sees, touches, or logs plaintext. It moves opaque envelope strings between Veil's app layer and Telegram's API. The channel monitoring set controls which chats are listened to — messages from all other chats are discarded silently.

Public API

class TelegramBridge:
    def __init__(self, api_id: int, api_hash: str, session_path: Path,
                 monitored_channels: set[int] | None = None): ...

    async def connect(self) -> None:
        """Start Telethon client, register NewMessage handler."""

    async def disconnect(self) -> None:
        """Disconnect the Telethon client cleanly."""

    async def send(self, channel_id: int, envelope: str) -> None:
        """Send envelope string to a Telegram chat. Raises RuntimeError if not connected."""

    async def on_receive(self, callback: Callable[[int, str], Awaitable[None]]) -> None:
        """Register the receive callback (one at a time). Safe to call before connect."""

    async def create_channel(self, user_ids: list[int], name: str) -> int:
        """Create Telegram group, add users, return chat ID. Raises RuntimeError if not connected."""

    async def get_self_user_id(self) -> int:
        """Return the authenticated user's Telegram ID. Raises RuntimeError if not connected."""

    def add_monitored_channel(self, channel_id: int) -> None:
        """Start monitoring a channel for incoming messages."""

    def remove_monitored_channel(self, channel_id: int) -> None:
        """Stop monitoring a channel. No-op if not present."""

Implementation Notes

  • TelegramBridge satisfies the Bridge Protocol structurally — Python Protocol matching is duck-typed, so no explicit class TelegramBridge(Bridge) inheritance is needed or appropriate.
  • on_receive is intentionally safe to call before connect(). The callback is stored on the instance and picked up by the message handler once the client is started. This allows app-layer wiring to happen in any order.
  • The NewMessage handler is registered inside connect() as a closure so it has direct access to the live monitored_channels set and _receive_callback. Because both are instance attributes (mutable), changes to the monitored set after connection take effect immediately without re-registering the handler.
  • remove_monitored_channel uses set.discard (not remove) so removing a channel that isn't monitored is a silent no-op rather than a KeyError.
  • Session management: Telethon creates a .session SQLite file at the configured path. First connection prompts for phone number and auth code interactively; subsequent connections are automatic. Future work (Phase 6) should encrypt this file at rest using the user's passphrase-derived key from Phase 2.
  • Telethon was already listed in pyproject.toml — no dependency changes were needed. The only import from Telethon is TelegramClient, events, and CreateChatRequest.
