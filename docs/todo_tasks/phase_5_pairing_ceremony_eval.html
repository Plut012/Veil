Component Purpose

The pairing ceremony is the moment two people establish encrypted communication. It happens in person. One QR scan bootstraps everything: key exchange, Telegram channel creation, and contact registration.

Two roles exist: the initiator (shows QR) and the joiner (scans QR). The initiator generates a 256-bit key and encodes it in a QR code alongside their Telegram user ID, display name, and envelope template. The joiner scans the QR, creates a Telegram group, sends an encrypted handshake, and saves the contact. The initiator detects the handshake, decrypts it, and saves the joiner as a contact. Pairing is complete with no server involvement.

QR Payload Format

{
  "v": 1,          // protocol version for future compatibility
  "key": "<base64>", // 256-bit symmetric key
  "tid": 12345,    // initiator's Telegram user ID
  "name": "Alice", // initiator's display name
  "env": "~~ {ciphertext} ~~"  // initiator's envelope template (may be empty)
}

Fields are abbreviated (tid, env) to keep payload compact — large QR payloads produce denser codes that are harder to scan. The key is URL-safe base64-encoded for JSON serialization.

Implementation Notes

  • Field access order in parse_qr_payload: Required fields (key, tid, name) are extracted into local variables before any decoding occurs. This ensures KeyError fires on truly missing fields rather than being masked by a downstream decode error on an invalid-but-present value.
  • parse_handshake_message never raises: The entire body is wrapped in a bare except Exception: return None guard. Wrong keys, malformed base64, invalid JSON, and missing type fields all silently return None. The handshake type field ("type": "veil_handshake") is the final validation gate — messages that decrypt correctly but aren't handshakes also return None.
  • telegram_user_id=0 for initiator: When the initiator completes pairing, they do not know the joiner's Telegram user ID from the handshake alone. The Telegram event delivers that information at the app layer. Setting it to 0 signals "unknown from handshake" — the app layer can update the contact once it has the sender's ID from the incoming message event.
  • Pending pairing state: The initiator holds QRPayload in memory between initiate_pairing() and complete_pairing_as_initiator(). Nothing is persisted until the handshake arrives. If pairing is cancelled, the in-memory payload is discarded with no cleanup needed.
  • QR code generation: Uses the qrcode library (already in pyproject.toml). Output is PNG bytes via io.BytesIO. The QR image is returned to the caller — the UI layer decides how to display it.
  • No new dependencies: qrcode and pillow were already declared in pyproject.toml. The module uses only standard library plus these two packages and existing Veil modules.
