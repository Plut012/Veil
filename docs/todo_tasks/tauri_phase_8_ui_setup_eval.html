Veil — Phase 8: UI-Based Setup Flow

Evaluation checklist for the setup flow implementation. Replaces all stdin prompts with an in-app multi-step setup UI.

Architecture

State model: VeilState now holds store: Mutex<Option<IdentityStore>> and bridge: Mutex<Option<TelegramBridge>>. Both are None at startup. Setup commands populate them lazily.

App Launch

  • No stdin prompts
  • State starts empty
  • Frontend queries status
→

Setup Flow

  • Config (first run)
  • Passphrase (every run)
  • Telegram auth (if needed)
→

Chat View

  • Contacts loaded
  • Messages stream live
  • All commands active

Acceptance Criteria

✓
App launches with no terminal interaction
main.rs has no prompt() calls, no rpassword usage, no stdin reads. State starts with store: None, bridge: None.
✓
get_setup_status correctly detects all states
Returns "needs_config" when api_id == 0 or api_hash empty. Returns "needs_passphrase" when store is None. Returns "needs_telegram_auth" when bridge is None or self_user_id == 0. Returns "ready" when bridge is connected with valid self_user_id.
✓
Config step saves API credentials and display name
submit_config writes api_id, api_hash, display_name to config.toml. Next call to get_setup_status advances past "needs_config".
✓
Passphrase step initializes IdentityStore and TelegramBridge
submit_passphrase: creates IdentityStore, creates TelegramBridge, calls connect_unauthenticated(). If session valid, calls finalize_connection() and returns "ready". Otherwise returns "needs_telegram_auth".
✓
Telegram auth handles phone → code → optional 2FA
request_telegram_code stores LoginToken in state. submit_telegram_code returns "ready" or "needs_2fa". submit_2fa_password completes 2FA. All intermediate tokens stored in VeilState.
✓
After setup, main chat view appears with contacts loaded
+page.svelte: when SetupView dispatches "complete", onSetupDone() is called which loads contacts and sets up message/pairing listeners. setupComplete flag toggles from SetupView to app shell.
✓
Subsequent launches skip config, show passphrase only
get_setup_status checks api_id first. If already configured, returns "needs_passphrase". SetupView maps this status to the passphrase step directly.
✓
Setup UI is minimal — fields only, no wizard chrome
SetupView: centered on screen, dark background, inputs with bottom-border only, placeholder text instead of labels, accent-colored button, muted red errors inline.
✓
cargo build succeeds
src-tauri/ compiles with warnings only (no errors). All existing types, traits, and modules preserved.
✓
npm run build succeeds
Frontend builds to dist/ with no errors. Accessibility warnings for autofocus are expected and benign in a desktop Tauri context.
✓
All cargo test passes (54/54)
No regressions. Bridge tests, identity store tests, envelope tests, pairing tests, config tests all pass.

Key Design Decisions

Bridge auth split: TelegramBridge.connect() is now split into connect_unauthenticated() (opens session, checks auth) and finalize_connection() (reconnects with listener spawned). This allows UI-driven auth between the two calls.

Reconnect after auth: After sign-in, the bridge disconnects and reconnects from the now-authorised session file. This gives a clean updates channel for the listener. The original unauthenticated connection's updates_rx is discarded.

Token storage: LoginToken and PasswordToken are stored in VeilState as Mutex<Option<T>> between the multi-step Telegram auth commands. Tokens are consumed (taken) when used.

Existing commands unchanged in behaviour: list_contacts, send_message, initiate_pairing, complete_pairing, update_envelope, set_theme now unwrap the Option with .as_ref().ok_or("not initialized")? instead of direct access. The error message propagates to the frontend if called before setup.
